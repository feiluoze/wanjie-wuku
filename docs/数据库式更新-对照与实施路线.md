## 数据库实际使用哪些机制

| 机制 | 已核对源码中的行为 | 武库应对齐的部分 |
|---|---|---|
| 原生填表 | 表及列编号、已有行、Note及新增/更新/删除触发规则；模型输出insertRow/updateRow/deleteRow | 按当前分类提供字段和写入触发条件，明确区分创建与更新 |
| 严格JSON | table_edit_ops_v1，insert带row；update带where/set；where零匹配或多匹配时报错 | 明确操作语义与唯一目标，保留合法空更新 |
| SQLite | 支持SQL变更协议，提示词声明DDL和定位规则；语法与权限仍需下游验证 | 借鉴表/字段白名单和明确定位，不把任意SQL执行权限开放给模型 |
| 行身份 | 新行由本地分配稳定row_id，不因删除后的显示位置变化而重用 | 沿用本地archiveId，显示名称不等于对象主键 |
| 工作副本 | staging session组装历史基线和本轮overlay，在受保护边界统一提交 | 逐层请求应看到本轮此前已验证的临时结果，不能每层都从旧档案开始 |
| 提交与并发 | 作用域、版本、写集、读写锁及提交/持久化边界 | 复用武库已有ChatStore事务与版本捕获，补充对象级写入统计与依赖检查 |
| 失败处理 | 按实际协议反馈具体错误；工具能力和严格JSON是可选路径 | 武库保留原回复与失败项，修复仅限原任务，不默认增加付费重试 |

数据库也不是天然防一切重复：原生insertRow路径会分配新行并追加，模型重复插入相同业务事实仍可能生成多行。SQLite能否阻止业务重复取决于模板UNIQUE约束等定义。不能把行ID唯一等同于语义唯一；不能把SQLite、原生DSL、严格JSON三条路径混为一谈。

## 武库当前差距与优先级

### P1：同一资源存在第二份可写余额入口——开发源码已收紧

离线复现：故事点资源账本余额为未知时，旧account.balance仍可接受999作为专用档案字段。实际账本没有入账，但档案会形成另一份当前余额，容易污染显示与正文记忆。

本轮开发修复精确绑定五处旧栏目：故事点account.balance、攻略系统points.balance、抽奖系统schedule.remaining、指数增长delta.balance、升变之印points.balance。模型声明不再提供这些可写列，直接ID及精确界面名称的写入都拒绝；手动表单只读，伪造该字段也不会写入；显示、专用统计、整理输入和正文记忆引用账本。其余收支依据继续可写，旧余额快照与历史保留。

这不是迁移旧存储，也不扫描删除历史描述里的金额。独立事件的历史收支金额仍是事实依据；后续须进一步区分“当前状态”与“历史回执”的记忆角色。

### P1：跨层整理缺少递进工作副本——已复现机制，尚未改写主链

archive-review.js中逐层请求闭包始终引用开始时的power；archive-history.js收集各层候选后才统一校验。合成复现的两次请求都看到空current，后一次看不到前一次候选对象。

该机制增加跨层重复创建或相互覆盖的风险，但不证明这次玩家档案里具体哪条重复。改造需要协调候选ID、失败保留、确认选择与重试，不能只在提示词里追加“不要重复”。

### P2：普通成果的新增/更新语义仍隐含

现有changes协议主要靠archiveId是否存在及名称匹配推断创建/更新；同名不同对象、同对象改名、总览与阶段事件交叉时缺少明确的分类唯一键。已有来源、归属、批次冲突和版本保护必须保留，不能通过放宽校验制造成功率。

### P2：成功统计不足以判断重复

当前accepted/saved是操作数量。应分别显示创建、更新、结束、无变化、失败，以及受影响的独立对象数；状态主表多次更新不作为多个新增成果。统计从实际提交前后差异计算，不能采信模型自报。

## 后续四步：先对齐写入契约，再扩大分类

1. **显式操作协议**：新请求声明insert/update/transition。update和transition必须定位已有archiveId或本批已分配临时引用；insert不允许冒填持久ID。不启用模型物理删除，结束使用状态变更。旧候选继续走旧版解析，不自动重写玩家数据。
2. **每类记录的身份与触发条件**：声明singleton/entity/event、身份字段、可修改字段、创建/更新/结束条件及记忆角色。原状态总览固定一行，人物/设施/技能按对象维护，独立订单与兑换按实际事件分别保留。只有原文明示的身份关系才能复用对象，不能靠近似名称静默合并。
3. **本批临时工作副本**：每层验证后进入隔离副本，向后续层提供临时对象引用；最终只提交玩家接受或既有自动模式准入的变化。取消、失败、聊天切换及来源变化不写真实档案。失败层未推进，后续依赖该层的变化重新核对。
4. **可审计的差异预览与统计**：列出操作、目标、变化字段、依据及保护原因，增加本地去重/无变化计数。按原文现有状态栏逐类验证后，再评估额外长期子表；不逐词条无限加特殊补丁。

## 验收场景

- 同一对象在三层只更新字段，最终一个对象，历史保留三次有依据的变化；没有变化不增加历史。
- 两笔真实不同订单即使商品相同也分别保留；不能按商品名合并事件。
- 改名明确指向原对象时复用ID；身份不明保留核对，不自动合并。
- 主表最新状态与事件流水分开，重复读取旧回执不重新发奖或叠加数值。
- 第2层失败时，第1层有效候选可恢复；依赖第2层的变化不能伪装成功。
- 更新期间切换聊天、改正文或变更资源绑定时旧结果不落盘。
- 旧模板、旧候选、自定义原文及MVU绑定保持其已有权限与兼容边界。
